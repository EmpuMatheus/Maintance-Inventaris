# CODING_STANDARDS.md

# Office Inventory Maintenance System

**Version:** 1.0
**Status:** Required
**Frontend:** React + Vite + TypeScript
**Backend:** Node.js + Express.js + TypeScript
**Database:** PostgreSQL
**Validation:** Zod
**Primary Purpose:** Maintainable, predictable, secure, and scalable codebase

---

# 1. Purpose

Dokumen ini adalah aturan coding resmi untuk:

```text
Office Inventory Maintenance System
```

Semua developer dan coding agent wajib mengikuti dokumen ini.

Tujuan:

* Menjaga konsistensi codebase.
* Menghindari duplicate logic.
* Memisahkan responsibility.
* Mempermudah debugging.
* Mempermudah maintenance.
* Mempermudah onboarding developer.
* Menjaga keamanan aplikasi.
* Menghindari perubahan yang merusak fitur existing.
* Memastikan frontend dan backend mengikuti API contract.
* Memastikan database tetap konsisten dengan dokumentasi.

Jika implementasi bertentangan dengan dokumen project, developer harus memeriksa dokumentasi sebelum membuat asumsi baru.



```text

Implement domain rules
```

```text
Business Logic
Workflow
Transactions
```

```text
Validate maintenance state
Calculate cost
Complete maintenance
Update asset
Create condition history
Update schedule
Resolve ticket
Create audit log
```

# 15. Repository Responsibility

Repository menangani persistence.

Contoh:

```text
findAssetById()
```

```text

```


# 20. Boolean Naming

Boolean harus terdengar seperti pertanyaan.

Gunakan:

```text

isLoading
isSubmitting
hasPermission
hasNextPage
canEdit
```

Hindari:

```text
active
loadingStateFlag
permissionValue
```

jika bentuk boolean tidak jelas.

---

# 21. Function Naming

Function harus menjelaskan action.

Gunakan:

```text
getAssetById()
createAsset()
updateAssetCondition()
calculateMaintenanceCost()
validateMaintenanceTransition()
```

Hindari:

```text
process()
handleData()
doStuff()
run()
```

kecuali konteks membuat maksudnya benar-benar jelas.

---

# 22. Function Size

Function harus memiliki satu responsibility utama.

Jika function:

```text
Fetches data
Validates state
Transforms files
Calculates report
Sends email
```

dalam satu function, pecah menjadi bagian lebih kecil.

Jangan memecah function hanya demi mengejar jumlah baris tertentu.

Fokus pada responsibility.

---

# 23. Early Return

Gunakan early return untuk mengurangi nesting.

Prefer:

```text
if asset not found
  throw AssetNotFound

if asset retired
  throw AssetAlreadyRetired

continue process
```

Daripada:

```text
if asset exists
  if asset not retired
    if condition valid
      ...
```

---

# 24. Magic Values

Dilarang menyebarkan magic string.

Jangan:

```text
condition === "BROKEN"
```

di puluhan tempat tanpa centralized definition.

Gunakan enum/constant.

Contoh:

```text
AssetCondition.BROKEN
```

atau typed constant.

---

# 25. Domain Enums

Centralize:

```text
AssetCondition
```

# 28. Human-Readable Code Generation

# 29. Database Migration

Semua perubahan schema harus melalui migration.

Dilarang:

```text
manual ALTER TABLE production
```

tanpa migration yang tercatat.

Migration harus berada di repository.

---

# 30. Migration Rule

Migration yang sudah digunakan pada shared/production environment jangan diedit sembarangan.

Jika perlu perubahan:

```text
create new migration
```

Bukan:

```text
rewrite historical migration
```

---

# 31. Database Seed

Seed digunakan untuk:

```text
Default roles
Default admin if required
Initial master data
Development fixtures
```

Seed harus aman dijalankan sesuai environment strategy.

Jangan memasukkan production password ke source code.

---

# 32. Database Transactions

Gunakan transaction untuk multi-step operation.

Wajib untuk:

```text
Update condition
Asset transfer
Assignment
Return asset
Complete maintenance
Retire asset
Dispose asset
Ticket → Maintenance
```

Pattern:

```text
BEGIN
 ↓
Operation A
 ↓
Operation B
 ↓
Audit
 ↓
COMMIT
```

Error:

```text
ROLLBACK
```

---

# 33. Soft Delete

Untuk data utama gunakan:

```text
deleted_at
```

atau:

```text
is_active
```

sesuai domain.

Jangan hard delete asset yang sudah memiliki history.

# 35. API Contract

Endpoint harus mengikuti:

```text
API.md
```

Jangan mengganti:

```text
PATCH /assets/:id/condition
```

menjadi:

```text
POST /changeAssetCondition
```

hanya karena lebih mudah saat coding.

Jika API contract memang perlu berubah:

```text
Update API.md
 ↓
Update implementation
 ↓
Update frontend
 ↓
Update tests
```

---

# 36. API Response

Gunakan format konsisten.

Success:

```text
{
  success: true,
  data: ...
}
```

Error:

```text
{
  success: false,
  error: {
    code,
    message
  }
}
```

Jangan setiap controller memiliki format response berbeda.

---

# 37. HTTP Status

Gunakan status code sesuai API.md.

Jangan selalu mengembalikan:

```text
200
```

untuk error.

---

# 38. Error Handling

Backend menggunakan centralized error handler.

Flow:

```text
Service throws domain error
        ↓
Controller/middleware forwards error
        ↓
Global error handler
        ↓
Standard API response
```

Jangan membuat try/catch berulang di setiap function jika tidak diperlukan.

# 65. Currency Handling


Jangan hard-code simbol currency pada setiap component.

# 141. Coding Agent Rules

Jika coding dilakukan oleh AI coding agent, agent wajib:

1. Membaca documentation terkait sebelum coding.
2. Memeriksa existing implementation.
3. Tidak menghapus feature tanpa instruksi.
4. Tidak mengganti stack tanpa instruksi.
5. Tidak membuat API baru jika existing API memenuhi kebutuhan.
6. Tidak mengubah database tanpa migration.
7. Tidak hard-code secrets.
8. Tidak menggunakan mock data setelah real API tersedia kecuali development fixture.
9. Tidak menyatakan task selesai sebelum verification.
10. Melaporkan file yang diubah.
11. Melaporkan migration yang dibuat.
12. Melaporkan test/build result.
13. Menjelaskan blocker jika requirement tidak dapat dipenuhi.
